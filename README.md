# kui_chai

ระบบบัญชีร้านหมวยกุยช่ายและสต็อกสินค้า

เว็บภาษาไทยรองรับมือถือ ใช้ชื่อผู้ใช้ร้านและรหัสผ่าน ตรวจสอบผ่าน Node.js backend ข้อมูลอยู่ใน Supabase PostgreSQL ไม่ใช้ Supabase Auth ในการเข้าเว็บร้านอีกต่อไป

## เปิดใช้งานครั้งแรก

1. หากยังไม่สร้างตาราง รัน `supabase/schema.sql` ครั้งเดียวใน SQL Editor ของ Supabase
2. รัน `supabase/stock-prices.sql` แล้วตามด้วย `supabase/admin-auth.sql` (เป็น transaction) สร้างตารางผู้ใช้และ session และจำกัดการเข้าฐานข้อมูลผ่านเซิร์ฟเวอร์
3. ใน `.env` ใส่ `SUPABASE_URL` และ `SUPABASE_SECRET_KEY` จาก Supabase Project Settings → API Keys → Secret keys ไม่ต้องส่ง key ผ่านแชต และห้ามนำไปใส่ JavaScript หรือ Git
4. รัน `npm run dev` เปิด http://127.0.0.1:5000
5. ล็อกอินด้วยชื่อผู้ใช้ `admin` รหัสผ่านเริ่มต้น `12345678`

`.env` ถูก ignore ใน Git ค่า publishable key เดิมไม่ใช้แล้ว หน้าเว็บไม่ขอกรอก URL/key และไม่มี key ฐานข้อมูลในไฟล์ที่ build

## ระบบล็อกอินและสิทธิ์

- `app_users` เก็บ bcrypt hash ผ่าน pgcrypto ไม่เก็บ plaintext password ในตาราง
- `app_login` เรียกได้เฉพาะ service_role ตรวจรหัสผ่านและล็อกบัญชี 15 นาทีหลังผิด 5 ครั้ง พร้อมล็อกแถวเพื่อป้องกันการนับผิดเมื่อยิงพร้อมกัน
- Session สุ่ม 256 บิต เก็บเฉพาะ SHA-256 hash ใน `app_sessions` คุกกี้เป็น HttpOnly, SameSite=Strict และ Secure เมื่อใช้ HTTPS หมดอายุ 24 ชั่วโมง ออกจากระบบแล้วลบ session ในฐานข้อมูล
- Backend ตรวจ session ทุกครั้ง จำกัด table/field ที่แก้ได้ และบังคับ owner_id จากผู้ใช้จริง ไม่รับ owner_id จากเบราว์เซอร์
- เปิด RLS ไว้ทุกตาราง และถอนสิทธิ์ anon/authenticated หลังรัน migration ข้อมูลอ่านได้ผ่าน backend ที่ตรวจ session เท่านั้น
- ห้ามใช้ static hosting เพียงอย่างเดียว เพราะต้องมี Node.js API ด้วย
- SQL migration ไม่เปลี่ยน ownership ของข้อมูลเก่า ข้อมูลบัญชี Supabase Auth เดิมจะอยู่ภายใต้ legacy account ที่ปิดไว้ หากมีข้อมูลเก่าจริงต้องเลือกย้าย ownership เพิ่มเติมก่อน admin จะเห็น
- รัน migration ซ้ำไม่รีเซ็ตรหัส admin ที่มีอยู่

รหัสเริ่มต้นถูกกำหนดใน SQL ตามที่ร้องขอ หากต้องการเปลี่ยน ให้รันใน SQL Editor:

```sql
update public.app_users
set password_hash=extensions.crypt('รหัสใหม่ของคุณ',extensions.gen_salt('bf',12)),failed_attempts=0,locked_until=null
where username='admin';
delete from public.app_sessions where user_id=(select id from public.app_users where username='admin');
```

## Deploy Vercel

Import source repository ใช้ `node build.mjs` และ output `public` ตาม vercel.json พร้อม Node.js function `api/index.mjs` ตั้ง `SUPABASE_URL` กับ `SUPABASE_SECRET_KEY` ใน Vercel Environment Variables แล้ว deploy ไม่ upload .env หรือ Excel ขึ้น repository

## ความหมายของยอดในรุ่นแรก

- รายรับ: ยอดขายจริงที่ผู้ใช้กรอก
- ต้นทุน: จำนวนสินค้าที่ลงบัญชี × ทุนต่อหน่วย ตามวิธีบันทึกใน Excel ไม่ใช่การคำนวณต้นทุนขายจากสต็อกอัตโนมัติ
- ค่าใช้จ่ายอื่น: ค่าแรง ค่าที่ และรายการที่เพิ่มในวันนั้น
- กำไรตามยอดบันทึก: รายรับ − ต้นทุน − ค่าใช้จ่ายอื่น
- ราคาขายเก็บเป็นข้อมูลประจำวัน ไม่ถูกนำไปแทนยอดขายจริง และการแก้วันหนึ่งไม่กระทบวันอื่น
- วันหนึ่งมีได้หนึ่งบัญชีต่อรอบขาย ถ้ามีแล้วให้เปิดรายการเดิมเพื่อแก้ไข
- รายงานเดือน/ปีรวมตามวันที่ขายจริง โดยปีเลือกเป็น ค.ศ.
- ต้นทุนสินค้าและรายจ่ายเก็บเป็น JSONB ในแถวบัญชีรายวัน เพื่อบันทึกทั้งวันในคำขอเดียว ข้อมูลอยู่ใน PostgreSQL ไม่ใช่ไฟล์ JSON บนเซิร์ฟเวอร์เว็บ

## ขอบเขตรุ่นแรก

สต็อกในรุ่นนี้คืออุปกรณ์ แสดงคงเหลือตามประวัติเข้าออก สามารถติดลบเพื่อสะท้อนรายการขาดได้ การโอนต้องบันทึกออกและเข้าแยกกัน ยังไม่มีธุรกรรมโอนสองทางอัตโนมัติ ยังไม่รองรับตัดสต็อกสินค้าขาย การคืน/ของเสีย และบิลแนบ

ฐานข้อมูลร้านถูกล้างก่อนนำโค้ดขึ้น GitHub เริ่มใช้งานด้วยการเพิ่มสถานที่ สินค้า และรอบขายใหม่ ไม่มีข้อมูลบัญชีตัวอย่างใน repository ไฟล์ Excel ข้อมูลนำเข้า และไฟล์สำรองถูก ignore ไว้ในเครื่อง

ดาวน์โหลดรายงาน CSV เปิดด้วย Excel ได้ และสำรองข้อมูลเต็มเป็น JSON ได้จากหน้าตั้งค่า ยังไม่มีหน้ากู้คืนอัตโนมัติหรือการตั้งสำรองอัตโนมัติ ตรวจแพ็กเกจสำรองข้อมูลของ Supabase และเก็บสำเนาเป็นประจำ

## การตรวจสอบ

`npm test` ตรวจการคำนวณเดือน/ปี รอบข้ามเดือน และ backend authentication/authorization ด้วย mock database รวม login, cookie, hash, logout, การบังคับ ownership และการปฏิเสธคำขอที่ไม่มีสิทธิ์

`node build.mjs` เตรียม static files โดยไม่รวม server secret การทดสอบฐานข้อมูลจริงต้องรัน SQL และตั้ง secret key ก่อน ยังไม่มีผลทดสอบ migration บน PostgreSQL จริง

## ราคาสินค้าในสต็อก

รัน `supabase/stock-prices.sql` ใน SQL Editor เพื่อเพิ่มประเภทสินค้า ราคาทุน และราคาขาย รายการเดิมจะเป็นประเภทอุปกรณ์โดยไม่เปลี่ยนยอดเก่า ถ้าต้องการใช้ลงบัญชีขาย ให้แก้เป็นสินค้าขายและตั้งราคาที่หน้าสต็อก

หน้าบันทึกรายวันเลือกสินค้าจากสต็อกและใส่จำนวน ระบบคำนวณทุนจากราคาที่บันทึกไว้ Backend ดึงราคาเอง ไม่เชื่อราคาจากเบราว์เซอร์ เมื่อแก้บัญชีเก่าใช้ราคาของบัญชีนั้น การแก้ราคาที่สต็อกมีผลกับรายการวันใหม่เท่านั้น ยังไม่ตัดสต็อกจากยอดขายโดยอัตโนมัติ

## ของเหลือรายวัน

รายการวันใหม่มี ยกมา (อัตโนมัติ), รับเพิ่ม, เหลือปลายวัน, เสีย/แจก และส่งคืน ขายได้คำนวณจากยกมา + รับเพิ่ม - เหลือ - เสีย/แจก - ส่งคืน Backend คำนวณซ้ำและไม่เชื่อยอดยกมาหรือราคาที่ส่งจากเบราว์เซอร์

ยกยอดจากรายการล่าสุดของสินค้านั้นก่อนวันที่เลือกในรอบเดียวกัน รองรับวันหยุดและข้ามเดือน ราคาทุนใช้เฉลี่ยถ่วงน้ำหนักระหว่างมูลค่ายกมาและของรับเพิ่ม โดยเก็บราคาของรับเพิ่มประจำวันไว้ ต้นทุนขายหักเฉพาะที่ขาย เสีย/แจกคิดตามทุนเฉลี่ยในค่าใช้จ่าย ของเหลือ/ส่งคืนไม่คิดเป็นต้นทุนขาย

รายการเก่าที่ไม่มี inventory_version คงความหมายเดิม ไม่เดายอดเหลือย้อนหลัง หากมีวันถัดไปบันทึกแล้ว จะไม่อนุญาตเพิ่มวันแทรกหรือแก้จำนวนสินค้าในวันก่อนหน้า ยังแก้รายรับ/ค่าใช้จ่าย/หมายเหตุได้เมื่อจำนวนเดิมไม่เปลี่ยน เพื่อแก้จำนวนให้เริ่มจากวันล่าสุดย้อนกลับ ไม่มีการแก้ยอดวันถัดไปอัตโนมัติ

ของเหลือแสดงแยกแต่ละรอบในหน้าสต็อก การส่งคืนเป็นการบันทึกจำนวนออกจากรอบ ยังไม่เพิ่มเข้าคลังหรือโอนไปรอบอื่นอัตโนมัติ รายการเคลื่อนไหวที่บันทึกในหน้าสต็อกเป็นอีกบัญชีหนึ่ง ไม่รวมซ้ำกับยอดเหลือรายวัน

ข้อมูลใหม่เก็บใน items JSONB เดิม ไม่ต้องรัน SQL เพิ่มสำหรับช่องของเหลือ (ต้องมี stock-prices.sql จากขั้นราคาสินค้าแล้ว)
